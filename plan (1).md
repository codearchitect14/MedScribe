# MedScribe AI: Medical Documentation Automation Platform
### End-to-End Development Plan

---

## 1. Project Overview

MedScribe AI is a web-based clinical documentation automation platform for physicians and clinics. It converts raw doctor-patient conversation transcripts into structured SOAP notes and care plans, generates medical coding suggestions (ICD-10 diagnosis codes and CPT/HCPCS procedure codes), and provides a revenue and analytics dashboard for practice owners and administrators.

The platform is inspired by ambient clinical scribing products such as reteta.com, which capture doctor-patient encounters and produce SOAP notes, after-visit summaries, and coding drafts. This plan describes a comparable system built entirely from freely available, open-source, and free-tier technologies, suitable for a small team or solo developer to build, test, and deploy without licensing costs.

### 1.1 Core Capabilities

1. Ingest a raw doctor-patient transcript through three paths: live in-browser recording with real-time transcription, uploaded audio file, or pasted/typed text.
2. Generate a structured SOAP note (Subjective, Objective, Assessment, Plan) using large language models.
3. Generate a care plan document from the SOAP note (follow-up actions, medications, referrals, patient instructions).
4. Suggest relevant ICD-10 diagnosis codes and CPT/HCPCS procedure codes based on the note content, backed by a searchable medical code database. See Section 4.2 for how CPT's licensing restrictions are handled using the free, public HCPCS code set as the primary procedure code source.
5. Store all clinical artifacts (transcript, SOAP note, care plan, codes) per patient encounter in a secure, structured database.
6. Provide role-based authentication for clinicians, coders, and administrators.
7. Provide a revenue and analytics dashboard showing encounter volume, coding mix, estimated reimbursement, clinician productivity, and turnaround time.
8. Present a professional public-facing marketing website (home, product, features, pricing, about, contact) with a clear login entry point into the authenticated application.

### 1.2 System Architecture Summary

- Frontend: React web application (public marketing site plus authenticated application).
- Backend: Python, FastAPI, REST API.
- Database: PostgreSQL with the pgvector extension for semantic search over medical codes and historical notes.
- Embeddings: open-source Hugging Face sentence embedding models, self-hosted, no external embedding API cost.
- Large Language Models: two interchangeable providers, Groq (openai/gpt-oss-20b) and Google Gemini, both used through free tiers with automatic failover and load balancing between them.
- Authentication and Authorization: JWT-based auth with role-based access control, secure password hashing, and session management.
- Deployment: Docker containers, deployable on free or low-cost tiers (Render, Railway, Fly.io, or a self-managed VPS).

### 1.3 Design Principles

- Minimize LLM token usage per encounter by using a single well-structured prompt per generation step, deterministic templating for repeated formatting, and caching wherever content repeats.
- Treat the LLM as a text structuring engine, not a source of medical truth. Diagnosis and procedure codes are always resolved against a real, versioned code database and retrieved through vector search, then only ranked or explained by the LLM.
- Keep the system provider-agnostic. Any LLM call goes through an internal abstraction layer so the active provider (Groq or Gemini) can be swapped by configuration, not code change.
- Every clinical document generated by the system carries a visible disclaimer that it is AI-assisted and requires clinician review and sign-off before use in a medical record. This is a documentation productivity tool, not a diagnostic tool.

## 2. Problem Statement

Clinicians spend a disproportionate amount of their working day on documentation rather than direct patient care. Manual writing of SOAP notes, after-visit summaries, and care plans, combined with manual lookup of ICD-10 and CPT/HCPCS codes for billing, is repetitive, time-consuming, and a leading contributor to clinician burnout. Existing commercial ambient-scribing platforms solve this problem but are closed, expensive, and unavailable to smaller practices, students, or teams who want to build or study such a system.

There is a need for a self-buildable, fully functional reference implementation of a medical documentation automation system that:

- Takes an unstructured doctor-patient transcript and produces a clean, clinically formatted SOAP note within seconds.
- Extends that note automatically into a patient-facing or record-facing care plan.
- Cross-references the note content against real ICD-10 and CPT/HCPCS code sets to propose billing-ready codes, rather than relying purely on LLM generation, which is unreliable for exact code lookups.
- Gives administrators visibility into how documentation volume translates into coding mix, estimated revenue, and clinician efficiency, through a proper analytics dashboard.
- Is secure by design, since the data involved is clinical in nature, with authentication, authorization, and encryption applied throughout.
- Can be operated entirely on free-tier infrastructure and free or open-source software, so the system is reproducible by any developer without a budget for commercial APIs or licensed medical terminology databases.

This plan addresses that need with a concrete, phase-wise implementation path.

## 4. Dataset Section

The system needs three categories of data: clinical dialogue-to-note training/reference data, medical coding reference data, and synthetic test data for development. All sources below are free and public.

### 4.1 Doctor-Patient Dialogue to Clinical Note Datasets

These datasets are used to build prompt examples (few-shot templates), evaluate the SOAP note generation pipeline, and optionally fine-tune or validate an open-source model later.

1. MTS-Dialog
 - Description: 1,701 short doctor-patient conversations paired with clinical note sections, covering six specialties (general medicine, neurology, orthopedics, SOAP, dermatology, allergy/immunology).
 - Source: Hugging Face, dataset id `har1/MTS_Dialogue-Clinical_Note`, or the original repository `github.com/abachaa/MTS-Dialog`.
 - Usage: Use the training split to build few-shot examples for prompt engineering. Use the validation and test splits to measure the quality of generated SOAP notes against reference notes with ROUGE/BERTScore metrics.

2. ACI-BENCH
 - Description: Ambient Clinical Intelligence benchmark. Longer, full doctor-patient encounters paired with complete SOAP-style notes, including three conversation styles (virtual assistant, virtual scribe, natural conversation).
 - Source: Hugging Face, dataset id `mkieffer/ACI-Bench`, and the original release referenced in the Scientific Data paper "Aci-bench: a Novel Ambient Clinical Intelligence Dataset for Benchmarking Automatic Visit Note Generation."
 - Usage: Primary dataset for evaluating full-length encounter-to-note generation, since it mirrors real visit length and structure more closely than MTS-Dialog.

3. NoteChat
 - Description: Large set of synthetic patient-physician conversations generated conditioned on real clinical notes, useful for augmenting training/few-shot examples at scale.
 - Source: Hugging Face, dataset id `akemiH/NoteChat`.
 - Usage: Use as additional few-shot and stress-testing examples, particularly for less common note formats.

4. PriMock57 (optional, referenced in ACI-BENCH paper)
 - Description: 57 mock doctor-patient primary care consultations with transcripts and notes, recorded and transcribed.
 - Source: Search "PriMock57 GitHub" (Babylon Health release).
 - Usage: Additional small-scale validation set, useful for UI demo data.

### 4.2 Medical Coding Reference Data

1. ICD-10-CM
 - Source: CMS (Centers for Medicare and Medicaid Services) official site, free annual release files (ICD-10-CM code tables and index), and the World Health Organization ICD-10 browser.
 - Format: Fixed-width text and XML files with code, short description, and long description.
 - Usage: Load into PostgreSQL as a reference table `icd10_codes(code, short_description, long_description, chapter, category)`. Generate embeddings for each description using the Hugging Face embedding model and store them in a pgvector column for semantic search.

2. CPT (Current Procedural Terminology)
 - Note: Full CPT code sets are copyrighted by the American Medical Association and are not freely redistributable in full.
 - Free alternative for development: use the publicly available CMS Healthcare Common Procedure Coding System (HCPCS) Level II codes, which are free and public, as the primary procedure code set for the open-source build. Support a small, manually curated open sample of commonly cited CPT codes (E/M codes such as 99213, 99214 are widely documented in public CMS materials for illustrative and educational use) for demonstration purposes only, clearly labeled as sample data.
 - Source: CMS HCPCS quarterly release files, free download from cms.gov.
 - Usage: Load into a `procedure_codes` table identical in structure to the ICD-10 table, with the same embedding pipeline.

3. LOINC (optional, for lab/objective data structuring)
 - Source: Regenstrief Institute, free registration required, loinc.org.
 - Usage: Optional enrichment for the Objective section when lab values are mentioned in the transcript.

### 4.3 Synthetic and Development Test Data

- Use a script to synthesize additional realistic transcripts by combining MTS-Dialog and ACI-BENCH fields into a common internal schema. This becomes the seed data for local development, demos, and automated tests, so the team never needs real patient data during development.
- Store all seed/test data in `/data/seed/` in the repository, never in production tables directly, and load through a documented seeding script.

### 4.4 Data Handling Rule

No real patient data should ever be used in development, staging, or demo environments. Only de-identified public datasets or synthetically generated data are permitted outside of a properly secured, access-controlled, and compliant production environment.

## 5. Phase-Wise Development Plan

The plan is organized into ten phases, Phase 0 through Phase 9. Each phase lists objectives, detailed tasks, and the concrete deliverable that signals the phase is complete. Phases are meant to be worked sequentially, since each phase's deliverable is a dependency for the next. The one exception is that Phase 1 (database and data layer) and Phase 2 (authentication and authorization) touch largely separate parts of the codebase and can be worked on in parallel once Phase 0 is complete.

### Phase 0: Environment and Repository Setup

**Objective:** Establish the foundation so all later work happens in a consistent, reproducible environment.

**Tasks:**
- Initialize a monorepo with two top-level folders: `backend/` (FastAPI) and `frontend/` (React).
- Set up Python virtual environment and `pyproject.toml` or `requirements.txt` with pinned versions for FastAPI, SQLAlchemy, Alembic, pydantic, asyncpg, passlib, python-jose, celery, redis, sentence-transformers, httpx, pytest.
- Set up the React project with Vite, TypeScript, TailwindCSS, ESLint, Prettier.
- Create a `docker-compose.yml` with services: `postgres` (with pgvector extension enabled via an init script), `redis`, `backend`, `frontend`, `worker` (Celery worker).
- Create `.env.example` documenting every required environment variable, without real secrets: database URL, JWT secret, Groq API key, Gemini API key, Redis URL.
- Set up GitHub Actions workflow for linting and running backend and frontend tests on every pull request.
- Configure pre-commit hooks (black, isort, flake8 or ruff, mypy for backend; eslint, prettier for frontend).

**Deliverable:** `docker-compose up` boots Postgres with pgvector, Redis, an empty FastAPI app returning a health check, and an empty React app, all connected, with CI passing on an initial commit.

### Phase 1: Database Schema and Data Layer

**Objective:** Design and implement the full relational schema, including the pgvector-backed reference tables.

**Tasks:**
- Design core tables:
 - `organizations` (clinic/practice tenant)
 - `users` (id, email, hashed_password, full_name, role, organization_id, is_active, created_at)
 - `roles` enumerated as clinician, coder, admin, super_admin
 - `patients` (id, organization_id, external_reference, demographic fields, created_at); store only the minimum needed, no unnecessary PHI fields
 - `encounters` (id, patient_id, clinician_id, organization_id, status, created_at, raw_transcript, audio_reference nullable)
 - `soap_notes` (id, encounter_id, subjective, objective, assessment, plan, model_used, tokens_used, generated_at, reviewed_by, reviewed_at, status)
 - `care_plans` (id, encounter_id, content, generated_at, reviewed_by, reviewed_at)
 - `code_suggestions` (id, encounter_id, code_type [icd10/hcpcs], code, description, confidence_score, accepted boolean)
 - `icd10_codes` (code, short_description, long_description, chapter, category, embedding vector)
 - `procedure_codes` (code, description, category, embedding vector)
 - `billing_records` (id, encounter_id, codes applied, estimated_reimbursement, billed_amount, payer, status, created_at)
 - `audit_logs` (id, user_id, action, entity_type, entity_id, timestamp, ip_address)
 - `llm_usage_logs` (id, provider, model, tokens_input, tokens_output, latency_ms, encounter_id, created_at) used for cost/analytics tracking
- Enable the `vector` extension in PostgreSQL and add vector columns (dimension matching the chosen embedding model, e.g. 384 for MiniLM) to `icd10_codes` and `procedure_codes`, plus an optional `note_embeddings` table for semantic search across historical notes.
- Write Alembic migrations for every table above.
- Write a data loading script that parses the CMS ICD-10-CM and HCPCS release files, inserts them into their respective tables, generates embeddings via the self-hosted Hugging Face model, and populates the vector column.
- Write the seed script that loads MTS-Dialog and ACI-BENCH samples into a local development dataset matching the `encounters` schema, for demo and test purposes only.
- Create appropriate indexes: b-tree indexes on foreign keys and lookup columns, HNSW or IVFFlat index (via pgvector) on the embedding columns for fast approximate nearest neighbor search.

**Deliverable:** A fully migrated database with ICD-10 and HCPCS reference tables populated and embedded, plus a seeding script that produces realistic demo encounters end to end.

### Phase 2: Authentication and Authorization

**Objective:** Secure, production-grade auth system with role-based access control.

**Tasks:**
- Implement user registration (admin-invited only, no public self-signup, since this is a clinical system) and login endpoints using OAuth2 password flow.
- Hash passwords with bcrypt via passlib. Never store plaintext passwords.
- Issue short-lived JWT access tokens (fifteen to thirty minutes) and longer-lived refresh tokens (seven days), stored as httpOnly, secure cookies for the refresh token, and in memory on the frontend for the access token.
- Implement RBAC middleware/dependency in FastAPI that checks the authenticated user's role against the required role(s) for each endpoint. Roles: clinician (create/view own encounters), coder (view and adjust codes across an organization), admin (manage users, view analytics), super_admin (manage organizations).
- Implement organization-level data isolation: every query is automatically scoped to the requesting user's `organization_id`, enforced at the query layer, not just in the UI.
- Implement password reset flow via email token (use a free transactional email provider such as Resend or Brevo free tier, or log to console in local development).
- Add rate limiting on authentication endpoints using Redis (e.g. five failed attempts per fifteen minutes per account) to prevent brute-force attacks.
- Add audit logging for login, logout, password change, and role changes into `audit_logs`.
- Implement CSRF protection for cookie-based refresh flow and CORS configuration restricted to the deployed frontend origin.
- Encrypt sensitive fields at rest where appropriate (e.g. patient identifiers) using application-level encryption (Python `cryptography` library, Fernet symmetric encryption with a key stored in environment configuration/secrets manager, never in source control).
- Enforce HTTPS/TLS in all non-local environments and set strict security headers (HSTS, X-Content-Type-Options, X-Frame-Options, Content-Security-Policy) via FastAPI middleware.

**Deliverable:** Working login, logout, refresh, and password reset flows, with role-based route protection verified by automated tests for each role, and audit logs recording all auth events.

### Phase 3: LLM Orchestration Layer (Groq and Gemini, Token-Efficient Design)

**Objective:** Build a single internal abstraction that both the SOAP note pipeline and the coding pipeline call, so the two free-tier LLM providers can be used interchangeably and efficiently.

**Tasks:**
- Create an internal module `llm_gateway` exposing a single function `generate(task_type, prompt, context)` that:
 - Selects the active provider based on a configurable strategy: primary provider first, automatic failover to the secondary provider on error or rate limit response, and simple round-robin load balancing across both providers if both are within quota.
 - Tracks remaining quota per provider in Redis (requests per minute, requests per day counters) so the gateway proactively switches provider before hitting a 429 response, rather than reacting to failures.
 - Logs every call into `llm_usage_logs` with tokens used and latency, for both cost auditing and the analytics dashboard.
- Implement provider adapters:
 - `GroqAdapter` calling the Groq chat completions endpoint with model `openai/gpt-oss-20b`.
 - `GeminiAdapter` calling the Gemini `generateContent` endpoint with a Flash-tier model.
- Design prompts to minimize token usage per end-to-end flow:
 - Use one single combined prompt per encounter for SOAP note generation that returns all four SOAP sections in one structured JSON response, instead of four separate calls.
 - Use a short, fixed system prompt reused across all calls, since both providers support prompt caching for repeated prefixes, reducing effective token cost on repeated calls.
 - Do not send the full transcript twice. Generate the SOAP note first, then generate the care plan using only the already-produced Assessment and Plan sections as input context, not the raw transcript again. This cuts the second call's input size significantly.
 - For code suggestion, never ask the LLM to invent ICD-10 or CPT/HCPCS codes from memory. Instead, first retrieve the top-k candidate codes via pgvector similarity search against the Assessment section embedding, and only send those k short candidate descriptions (typically five to ten) plus the Assessment text to the LLM, asking it to select and briefly justify the best matches. This keeps the coding call small and keeps codes accurate, since they come from the real reference table, not from model memory.
 - Cap max output tokens explicitly per call type (e.g. 500 for SOAP note, 300 for care plan, 200 for coding justification) to prevent runaway generations.
 - Enforce a strict JSON output schema (using function calling / structured output support on both providers where available, otherwise a strict prompt template with a JSON-only instruction and a validation/retry step) so no re-generation is needed due to parsing failure.
- Implement a request-level cache: if the same transcript hash has already been processed, return the cached result rather than calling the LLM again.
- Write unit tests using mocked provider responses, and a small integration test suite that runs against the real free tier keys in CI on a limited, scheduled basis only (not on every push) to avoid exhausting the free quota.

**Deliverable:** A working `llm_gateway.generate()` function used consistently across the app, verified failover between Groq and Gemini, and a measured token cost per end-to-end encounter (transcript to SOAP note to care plan to coded suggestions) that stays within a documented, minimized budget.

### Phase 4: Core Clinical Pipeline (SOAP Notes, Care Plans, Coding)

**Objective:** Implement the primary product functionality.

**Tasks:**
- Build the embedding module using a Hugging Face sentence-transformers model (general-purpose `sentence-transformers/all-MiniLM-L6-v2` for speed, with an optional swap to a biomedical model such as `pritamdeka/S-PubMedBert-MS-MARCO` for higher clinical accuracy) served locally through a small internal FastAPI microservice or an in-process function, so no external embedding API is ever called.
- Build the transcript ingestion endpoint:
 - Accepts raw text transcripts pasted or uploaded directly.
 - Accepts a completed audio file upload and runs it through self-hosted faster-whisper in a single batch pass to produce the transcript.
 - Performs basic cleaning (speaker label normalization, removal of filler words) before sending to the LLM stage, regardless of which of the two input paths produced the transcript. A third input path, live in-browser recording, is added in Phase 5 and feeds into this same endpoint once transcription completes.
- Build the SOAP note generation service:
 - Calls `llm_gateway.generate()` with the combined SOAP prompt described in Phase 3.
 - Validates the JSON response against a Pydantic schema with the four sections.
 - Persists the result into `soap_notes` with `status = draft`.
 - Exposes an endpoint for the clinician to edit any section manually and mark the note as `reviewed` or `finalized`, since human review is mandatory before the note is considered official.
- Build the care plan generation service:
 - Takes the finalized or draft Assessment and Plan sections as input.
 - Produces a structured care plan: diagnosis summary, recommended follow-up actions, prescribed or recommended medications (flagged clearly as suggestions requiring clinician confirmation), patient education notes, and next appointment guidance.
 - Persists into `care_plans`, editable and reviewable in the same way as SOAP notes.
- Build the medical coding service:
 - Generates an embedding for the Assessment section.
 - Runs a pgvector cosine similarity search against `icd10_codes` and `procedure_codes` to retrieve the top candidates.
 - Sends the candidates plus context to the LLM for ranking and a short justification per suggested code.
 - Persists results into `code_suggestions` with a confidence score, allowing the coder role to accept, reject, or replace each suggestion.
- Build an encounter status workflow: `transcribed -> note_generated -> under_review -> finalized -> coded -> billed`, enforced at the API layer so encounters cannot skip required review steps.
- Write end-to-end tests using the seeded MTS-Dialog/ACI-BENCH data to confirm the full pipeline produces well-formed, schema-valid output for a representative sample of real dialogue types.

**Deliverable:** A clinician can submit a transcript and receive, within seconds, a structured SOAP note, an editable care plan, and a ranked list of accurate ICD-10 and HCPCS code suggestions, all persisted and auditable.

### Phase 5: Live Transcription (Whisper and WebSockets)

**Objective:** Allow a clinician to start a live encounter recording directly in the browser and see the transcript appear in near real time, adding a third input path alongside the pasted text and uploaded audio file ingestion built in Phase 4.

**Tasks:**
- Backend WebSocket endpoint:
 - Add a FastAPI WebSocket route, for example `/ws/encounters/{encounter_id}/live-transcribe`, authenticated using the existing JWT (passed as a query parameter or during the initial handshake message, since browser WebSocket clients cannot set custom headers).
 - On connection, create or attach to an `encounters` row with `status = recording` and open a streaming session tied to that encounter.
 - Accept binary audio chunks pushed from the frontend at a fixed interval (for example every one to two seconds of audio).
- Streaming transcription engine:
 - Run faster-whisper self-hosted, loaded once at process startup (recommended model size `small` or `base` for a reasonable balance of speed and accuracy on free-tier or modest hardware, `medium` if server resources allow).
 - Maintain a small rolling audio buffer per active session. Run inference on the buffer at each chunk arrival using a sliding-window approach, emitting partial (unconfirmed) transcript text quickly and a corrected/final transcript segment once enough trailing audio confirms a stable sentence boundary. This mirrors how commercial live-captioning systems distinguish interim results from final results.
 - Run each active session's Whisper inference in its own background task or worker process so one long encounter does not block other requests. If running Whisper in the same process, use a queue and a fixed-size worker pool sized to the host's CPU cores, since free-tier hosts typically have limited CPU. If concurrent live sessions exceed the pool size, queue the request and inform the frontend of the wait rather than dropping audio.
 - Append each finalized segment to the growing `raw_transcript` field on the `encounters` row, with periodic checkpoint saves to the database (for example every ten to fifteen seconds) so no progress is lost if the connection drops.
 - Push both partial and final transcript segments back to the frontend over the same WebSocket connection as small JSON messages, tagged with a type (`partial` or `final`) and a running sequence number.
- Frontend live recording component:
 - Use the browser MediaRecorder API (or the AudioWorklet API for finer control over chunk size and sample rate) to capture microphone audio, request microphone permission explicitly, and show a clear recording indicator and timer.
 - Open a WebSocket connection to the backend endpoint when the clinician presses "Start recording," stream audio chunks continuously, and render incoming partial transcript text in a lighter, provisional style and finalized text in normal style, similar to live captioning.
 - Provide pause, resume, and stop controls. On stop, close the WebSocket cleanly, mark the encounter `status = transcribed`, and route directly into the existing SOAP note generation flow from Phase 4, using the transcript that was just captured, with no additional manual step required.
 - Handle reconnection: if the WebSocket drops mid-recording, attempt automatic reconnect with the same encounter id and resume streaming without losing the transcript captured so far, since it is checkpointed on the backend.
 - Display a clear, visible notice during recording that the audio is being processed for transcription only, is not stored as a raw audio file beyond what is needed for processing, and requires patient consent to record, consistent with the security and consent posture described in Phase 9.
- Resource and cost control:
 - Since this feature runs entirely on self-hosted, open-source Whisper rather than a paid API, the only constraint is server CPU/GPU capacity, not per-minute billing. Document the expected CPU load per concurrent live session so the team can size the deployment target (for example, a single `small` model instance on a modest free-tier VM can typically support a small number of concurrent live sessions; benchmark this on the actual deployment target before relying on it for multiple simultaneous clinicians).
 - Add a configuration flag to fall back to file-based, non-live transcription (record locally in the browser, upload the completed audio file at the end, transcribe in one batch call) for deployments where live streaming CPU load is not practical, so the feature degrades gracefully rather than failing outright.
- Testing:
 - Write backend tests that simulate a WebSocket client streaming a short pre-recorded audio sample and assert that partial and final transcript messages arrive in order and that the final saved `raw_transcript` matches the expected reference text within a reasonable word error rate.
 - Manually test on at least two browsers (Chrome and Firefox) for microphone permission and WebSocket behavior differences.

**Deliverable:** A clinician can press "Start recording" on the New Encounter screen, speak or hold a live conversation, watch the transcript populate in the browser in near real time, press "Stop," and be taken directly into the SOAP note generation flow using the transcript that was just produced, with no manual upload step required.

### Phase 7: Revenue and Analytics Dashboard

**Objective:** Build the administrative analytics product surface.

**Tasks:**
- Design and implement nightly (or on-demand) aggregation jobs (Celery beat scheduled tasks) that compute:
 - Encounter volume per day/week/month, per clinician, per organization.
 - Coding mix: distribution of ICD-10 chapters and HCPCS categories used.
 - Estimated reimbursement: a configurable rate table mapping codes to typical reimbursement values (loaded as reference data, adjustable by an admin, not hardcoded), multiplied by coded encounter counts, to produce an estimated revenue figure. Clearly label this as an estimate, not an actual billed amount, unless a real billing integration is connected.
 - Turnaround time: average time from transcript submission to finalized note, and from finalized note to coded/billed status.
 - LLM cost and usage: token consumption and estimated cost per provider, sourced from `llm_usage_logs`, useful for monitoring free-tier quota usage.
 - Clinician productivity: encounters completed, average review edits per note, average time to finalize.
- Expose analytics through dedicated read-only, paginated, role-restricted (admin/super_admin only) API endpoints, pre-aggregated rather than computed on the fly on every request, for performance.
- The frontend analytics dashboard that consumes these endpoints is built in Phase 8.
- Add CSV/Excel export for any analytics table, since finance and operations staff typically need raw exports.

**Deliverable:** A working analytics API and backing aggregation jobs producing accurate, explainable revenue and productivity metrics from real encounter and coding data.

### Phase 8: Frontend Application (Public Website and Authenticated App)

**Objective:** Build a professional, Fortune 100 quality public website plus a clean, efficient authenticated application, in a single React codebase with clear separation between public and authenticated routes.

#### 8.1 Public Marketing Website

The public site must read as an enterprise healthcare technology product, not a prototype. Structure and content guidance:

- **Navigation bar:** Logo/wordmark on the left, links to Product, Solutions, Pricing, Resources, About, Contact in the center, and a clearly styled "Log in" button on the right, plus a primary call-to-action button such as "Request a demo." The login button must be present on every public page, not just the homepage.
- **Homepage:**
 - Hero section: a strong headline focused on clinician time saved (for example, framing around reducing documentation time and administrative burden), a supporting subheadline, a primary call-to-action button ("Get started" or "Request a demo"), and a secondary "Watch demo" link. Include a high-quality product screenshot or illustration of the SOAP note generation screen, using either an actual application screenshot once available or a professionally styled mock illustration in the interim (do not use real patient data in any screenshot).
 - Trust bar: a row of illustrative client/partner logos or compliance badges (for example, HIPAA-aligned security messaging, SOC 2-style readiness language) to convey enterprise credibility. Do not fabricate specific certifications the system does not actually hold; phrase as "built with HIPAA-aligned security practices" rather than claiming certification.
 - Feature sections, each with a heading, two to three sentences of supporting copy, and a relevant icon or image: ambient transcription, automated SOAP notes, automated care plans, AI-assisted medical coding, analytics and revenue insights, and enterprise-grade security.
 - "How it works" section presented as a simple three or four step visual flow: record or paste the encounter, review the generated note, confirm codes, sync to your workflow.
 - Specialty or use-case section, listing supported clinical specialties or care settings.
 - Testimonial/quote section (use realistic, clearly fictional example quotes attributed to generic roles such as "Family Medicine Physician," never real named individuals or organizations).
 - Metrics/impact section with illustrative statistics on time saved and documentation speed, clearly framed as example/target metrics if real production data does not yet exist.
 - Final call-to-action banner before the footer.
 - Footer: sitemap-style link columns (Product, Company, Legal, Resources), social links, copyright line, and a compliance/privacy statement link.
- **Product page:** deeper walkthrough of the SOAP note, care plan, and coding features, each with its own screenshot and short explanation.
- **Solutions page:** organized by audience (independent clinicians, multi-provider clinics, health systems) with tailored value propositions for each.
- **Pricing page:** simple tiered pricing table (for example Starter, Professional, Enterprise) with feature comparisons and a "Contact sales" option for Enterprise. Since underlying LLM usage is free-tier, pricing here is illustrative business-model content, not a technical constraint.
- **About page:** mission statement, company story, and a values section.
- **Contact page:** a professional contact form (name, email, organization, message) that submits to a backend endpoint and stores the inquiry, plus company contact details.
- **Visuals:** use royalty-free, professional healthcare-context photography and iconography (for example from Unsplash or Pexels, both free for commercial use, or a consistent icon set such as Lucide or Heroicons, both open-source) throughout. Maintain one consistent color palette, one heading font and one body font, and consistent spacing and corner-radius rules across every page, so the site feels designed by a single team rather than assembled from templates.

#### 8.2 Authenticated Application

- **Login page:** clean, centered card, email and password fields, "Forgot password" link, and clear error states. Reached from the "Log in" button on every public page.
- **Dashboard (role-aware landing page):**
 - Clinician view: list of their own recent encounters, a prominent "New encounter" action, and quick status indicators (draft, under review, finalized).
 - Admin/coder view: organization-wide encounter queue, coding review queue, and a summary analytics panel.
- **New Encounter flow:** patient selection or creation, then a choice of three input modes: start a live recording (using the WebSocket-based live transcription component from Phase 5, with a real-time transcript view and start/pause/stop controls), upload a pre-recorded audio file, or paste an existing text transcript. After transcript capture completes, a submit action triggers the backend pipeline, with a real-time or polling-based status indicator while generation runs.
- **Encounter detail view:** three-panel or tabbed layout showing the raw transcript, the generated SOAP note (editable, section by section), the care plan (editable), and the coding suggestions (with accept/reject controls per code and a running total of accepted codes). Include a clear "Finalize note" action gating the workflow status.
- **Patients view:** searchable, paginated patient list and patient detail page showing encounter history.
- **Analytics dashboard (admin/coder roles):** chart-driven view built with an open-source charting library (Recharts) showing encounter volume trends, coding mix breakdown, estimated revenue trend, clinician productivity table, and LLM usage/cost panel. Include date-range filters and CSV export buttons.
- **Settings/administration:** user management (invite, deactivate, change role), organization profile, and reimbursement rate table configuration (used by the analytics estimate).
- **Design system:** define a shared design token set (colors, spacing, typography, shadows, border radius) once and reuse it across both the public site and the authenticated app, so the transition from marketing site to logged-in product feels seamless and consistently premium.

**Deliverable:** A deployed React application with a complete, professional public marketing site and a fully functional authenticated application covering every workflow from Phases 4, 5, and 7, responsive on desktop and tablet at minimum.

### Phase 9: Security, Compliance Review, Testing, and Deployment

**Objective:** Final hardening, verification, and release.

**Tasks:**
- Conduct a full data-flow review: confirm no clinical text is logged in plaintext outside the database, confirm all traffic is served over TLS, confirm JWTs are short-lived and refresh tokens are rotated on use.
- Conduct a dependency security audit (`pip-audit` for backend, `npm audit` for frontend) and resolve or document any findings.
- Review and document the system's alignment with HIPAA-style safeguards: access controls, audit logging, encryption at rest and in transit, minimum necessary data collection, and a documented data retention/deletion policy. Note explicitly in the documentation that formal HIPAA compliance requires a signed Business Associate Agreement with hosting/LLM providers and a full compliance audit, which is outside the scope of a free-tier reference build, so production use with real patient data should not occur until that is addressed.
- Run full regression test suite (backend and frontend) and fix any failing tests before release.
- Write deployment scripts/CI pipeline for automatic build and deploy to the chosen free-tier hosting targets on merge to the main branch.
- Set up basic uptime monitoring (free tier of UptimeRobot or similar) and error tracking (free tier of Sentry) in the deployed environment.
- Perform a final walkthrough of the entire flow, from public homepage, through login, through a full encounter generating a SOAP note, care plan, and codes, through the analytics dashboard, confirming everything works end to end on the deployed environment, not just locally.

**Deliverable:** A deployed, monitored, security-reviewed application accessible at a public URL, with the login flow reachable from the marketing site and the full clinical and analytics workflow verified in production.

## 6. Documentation Requirements

The repository must include clear, professional documentation, written in plain, factual language, with no informal wording and no use of the em dash character anywhere in any file.

- **README.md** at the repository root, containing: project name and one-paragraph description, architecture diagram or description, tech stack list, prerequisites, local setup instructions (clone, environment variables, docker-compose up, migrations, seeding), how to run tests, how to deploy, and a link to further documentation.
- **/docs/architecture.md:** detailed system architecture, data flow diagrams (can be described in text or included as image files), and the LLM gateway failover design.
- **/docs/database-schema.md:** full schema reference with table descriptions, generated or maintained alongside migrations.
- **/docs/api-reference.md:** summary of key endpoints, pointing to the live OpenAPI/Swagger documentation served by FastAPI at `/docs`.
- **/docs/datasets.md:** restates the dataset sources and loading instructions from Section 4 of this plan, kept up to date as the canonical reference.
- **/docs/security.md:** documents authentication, authorization, encryption, and the compliance notes from Phase 9.
- **/docs/llm-strategy.md:** documents the Groq/Gemini failover strategy, prompt design, and token minimization approach from Phase 3, so future maintainers understand why the prompts are structured the way they are.
- **/docs/live-transcription.md:** documents the WebSocket protocol between frontend and backend, the Whisper model sizing and concurrency limits, the checkpointing/reconnect behavior, and the batch fallback mode from Phase 5.
- **CONTRIBUTING.md:** coding standards, branch strategy, pull request process, and commit message conventions.
- **CHANGELOG.md:** maintained per release using a standard format such as Keep a Changelog.

All documentation must be kept current as the system evolves. Any change to the database schema, the LLM gateway, or the authentication model must be reflected in the corresponding documentation file in the same pull request that makes the change.
